# Deployment

Two settings decide whether a deployment is real or a demo:

| Variable | What happens without it |
|---|---|
| `DATABASE_URL` | Accounts and logs disappear. The app shows a banner saying so |
| `SECRET_KEY` | Every restart signs everybody out |

Everything below is about getting those two right. The Azure keys are
optional: with none of them the app still runs, on local rules.

## Storage, and why it used to lose everything

The app was backed by a SQLite file. On a serverless host that is a
promise it cannot keep:

1. **The filesystem is read-only** except `/tmp`, so the first write fails.
2. **The container is discarded between requests**, so even `/tmp` is
   gone by the next one, and two people using the app at the same time
   can be served by different containers holding different data.

That was survivable while the app was single user and the only casualty
was demo data. With accounts it is not: somebody creates a login, comes
back, and it does not exist.

So the app now speaks Postgres as well. Set `DATABASE_URL` and the same
SQL runs against it; leave it empty and it is SQLite on disk, which is
what you want locally. `/api/health` reports which one it got.

## Render, which sets this up for you

`render.yaml` declares the web service **and** a Postgres database, and
wires `DATABASE_URL` between them. There is nothing to copy by hand.

1. Sign in at render.com with GitHub and pick this repository
2. Render reads `render.yaml`. Accept the free plan for both the service
   and the database
3. Add the Azure variables in the dashboard. They are marked
   `sync: false` in the file precisely so they are never committed:
   `AZURE_OPENAI_ENDPOINT`, `AZURE_OPENAI_API_KEY`,
   `AZURE_OPENAI_DEPLOYMENT`, `AZURE_OPENAI_API_VERSION`,
   `AZURE_SPEECH_KEY`, `AZURE_SPEECH_REGION`,
   `AZURE_CONTENT_SAFETY_ENDPOINT`, `AZURE_CONTENT_SAFETY_KEY`
4. Deploy, then check `/api/health` reads `"storage": "persistent"` and
   `"backend": "postgres"`

`SECRET_KEY` is generated by Render once and kept, so a redeploy does not
sign anyone out. Render's free Postgres expires after a period, so check
the dashboard before relying on it past the presentation.

The free web service sleeps after about fifteen minutes of no traffic, so
the first request after a quiet spell takes a few seconds. The data is
still there: it is in the database, not the container.

## Vercel

Vercel can run this properly too, but it will not provision a database
for you, so that part is manual:

1. Get a Postgres connection string. Vercel's own marketplace (Neon) has
   a free tier, and so does Supabase. Azure Database for PostgreSQL works
   too and would keep the whole project on Azure credits
2. In the Vercel project, Settings → Environment Variables, add:
   - `DATABASE_URL` — the connection string, including `?sslmode=require`
   - `SECRET_KEY` — from `python -c "import secrets; print(secrets.token_hex(32))"`
3. Redeploy, and check `/api/health`

Without step 2 the deployment still works, but it is a demo: the banner
warns that accounts can vanish, and they will.

There is deliberately **no `vercel.json`**. One was added and it broke the
whole deployment with a 500: the `builds`/`routes` format is the legacy
config and it overrides Vercel's own detection, which was working.

## Locally, which is what the video should use

```bash
pip install -r requirements.txt
python -m scripts.seed
uvicorn app.main:app --reload
```

`scripts.seed` makes a `demo@local` account with password `demo1234` and
fills it with a month of history. Everything works, nothing sleeps, and
no network round trip sits between a click and the answer.

## Checking a deployment

```bash
curl https://<your-host>/api/health
```

```json
{
  "status": "ok",
  "storage": "persistent",
  "backend": "postgres",
  "accounts": 3,
  "agents": ["coach", "..."],
  "azure": { "openai": true, "speech": true, "content_safety": true }
}
```

- `storage: ephemeral` means accounts and logs will not survive
- `backend: sqlite` on a hosted deployment means `DATABASE_URL` is missing
- any `azure` flag `false` means that variable is missing on the host
- the app still runs with all of them false, on local rules and data

## Moving from a pre-accounts database

Every table gained a `user_id` when sign-in arrived, and
`CREATE TABLE IF NOT EXISTS` will not add a column to a table that is
already there. Startup notices an older SQLite file, renames it to
`<name>.pre-accounts` and builds a fresh one beside it. Nothing is
deleted, and nothing in such a file can belong to an account, because
accounts did not exist when it was written.

## Keys

`.env` is git-ignored and must stay that way. Keys live in the host's own
environment settings. `render.yaml` deliberately declares them without
values, and `DATABASE_URL` is wired from the database resource rather
than written down anywhere.
